# SQ8 batch admission remediation

The 9 November SQ8 batch comparison found a Veortex admission limit at B64/C4 for filtered searches that return payload. In the active-only diagnostic, extending `QDRANT_VEORTEX_SINGLETON_ADMISSION_WAIT_MS` from 90 ms to 1,000 ms still produced 5,694 HTTP 429 responses, with no correctness failures. Per-node `/metrics` evidence showed query-byte rejection deltas of 46,589, 26,733, and 27,039; the other circular-ring rejection reasons did not increase. The reservation limit was 402,653,184 bytes (384 MiB), and observed peaks reached 402,218,600 bytes on all three nodes. Rejection-counter events count individual query admissions, while the client report counts failed HTTP batches, so those counts are not expected to match. The failed diagnostic’s latency percentiles include fast 429 responses and should not be compared with the all-success candidate rows below.

The cause is the bounded query-byte reservation, not the singleton wait. Each filtered query conservatively reserves 1 MiB for its filter bitmap and, when payload is requested, another 1 MiB for raw payload, plus vector, filter, and result metadata. A B64 batch is fanned out into 64 query admissions; with four client requests in flight, that is up to 256 reservations per node. Filtered payload batches therefore exceed the 384 MiB default. Unfiltered payload batches have no filter-bitmap reservation and stayed below it. The 1-second singleton wait does not govern these explicit batch children.

The source change on `fix/ring-admission-budget-20261109` (`a1a2af190e6f03508efa0b9105b88507dec9f7aa`) only raises the validated configurable ceiling to 2 GiB; the default remains 384 MiB. A focused estimate test found that 256 query reservations total 541,936,640 bytes for active-only and 542,903,296 bytes for the narrow filter. The candidate profile therefore sets `QDRANT_VEORTEX_MAX_QUEUED_QUERY_BYTES=671088640` (640 MiB) on each node. This covers the target B64/C4 workload's estimated reservations with headroom. It is a bounded reservation limit, not memory preallocated at startup, and it is not a guarantee for higher concurrency, larger filters or payloads, or overlapping workloads. The profile leaves the singleton wait at 90 ms and the search timeout at 60 seconds; neither is changed to address this failure.

The 640 MiB V45.1 candidate passed all four focused B64/C4 category rows. Each had zero HTTP 429s and zero request, protocol, transport, or correctness errors. The exact-truth check passed for all 4,096 initial F32 queries and all 346,368 queries returned during timed measurement. The three focused Rust tests passed, and all three nodes reported the configured 671,088,640-byte cap and zero ring-rejection-counter deltas.

The original stock Qdrant 1.20 primary rows were reused rather than rerun, and the new binary was not remeasured at B1. These focused results establish that this workload fits the 640 MiB profile; they do not establish a universal absence of 429s or a causal performance-regression comparison.
